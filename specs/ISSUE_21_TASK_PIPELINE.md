## 证据与纠正

以下结论在实施前必须分开：

1. **不是缺少提交动作**：task_agent.py 的 answer → submit，team_agent.py → Plan(submit)，tasks.py → roleCommandMap[pioneer].submitAnswer/taskAnswer；run → cmd → 顶层 executeCmd。接任务由任务生命周期负责。现有端到端测试实测这一链路通过。真正待修的是获取材料效率、计划收敛与截止时间，不重建第二套互相冲突的协议。
2. **不是已证实对手零 LLM**：同一 Issue 的 R12 RES 明确含 prompt。R1 SUM 的空通道不能证明全局不调用。借鉴其批量探测和校验闭环，不照抄“纯离线”归因。
3. **塔上限未被推翻**：本地官方任务书 §4.5.1 明确全局同时最多 3 座。其他 Bot 的 OVERTURNED 字段是该 Bot 元数据，不是官方更正。
4. **不能把 70/90/116 当己方波次数直接翻倍**：原有第 1–3 夜每队 35/45/58 与双方总量相符；摘录末轮 robots=100、target_us=44 明确总量不等于我方目标。完整 targetTeam 分组缺失时保留待核，不变更波次。
5. **当前 HP 不是初始 HP**：开拓者 120、炮台 1355/1055 等观测可能已受伤；官方开拓者初始 200，一级基地 1500，建筑一级 1000。station 的 150 与用户摘录的 1500 矛盾，不能写回规则。
6. **任务时限不能由 episode 行号直接推定**：表内 R60–70 等不满 15；以 acceptTask 发出/确认和 timeoutRounds 为计时依据。奖励80+80和时限15属于此场景观测，运行时读取 playerTasks，不能变成全局常量。
7. **R368 后缺日志不是已证实 flush 故障**：须区分服务器停止收到请求、角色清空、进程退出与日志丢失；官方比分与最后日志均差30值得核对生存结算，不臆造具体原因。

## P1：文档驱动的求解工具与判题闭环

- API任务从真实文档解析接口/鉴权/分页/字段/格式，再构造有界请求与计算；不固定 heritage 路由、城市和答案。只请求题目授权的沙盒服务。
- 工程任务读取当前spec、相关文件与check结果；确定性文件/权限修复优先，复杂语义交LLM。对文件修改限定已确认工作区与允许路径，反向路径/链接逸出/任意扩权不执行。
- 先确定答案契约，再执行最小补丁、运行官方check、读取实际回执中的token，使用submitAnswer并观察判题反馈。不能将示例token、源码字符串、任意12位hex当成功token，不能读取验证器进程内存、绕过chroot或伪造check。
- 方法缓存只保存验证过的程序/文档关系和操作模式，不缓存城市答案、token、一次性密钥或别队上下文。
- 非模板任务回退通用Agent；结构化步骤帮助LLM减少往返，不替代它处理未知题意。

验收：API字段/端口/城市/分页随机变化；工程工作区与文件名随机变化、需chmod/改配置、check失败/超时/伪token、部分正确/错误答案再提交；序列化往返与串题隔离。脚本化模型测试证明控制链，不称为真实模型解题率。恢复API额度后至少3次真实模型重复，原失败证据不覆盖。

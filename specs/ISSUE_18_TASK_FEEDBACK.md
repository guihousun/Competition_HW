## 第一阶段：立即改进反馈与诊断

1. Issue 表单只要求描述现象并附可公开日志，版本/地图可选；无需用户填写规则编号、预期原理、复现定位。保留一次公开数据确认。启动 identity 自动提供可用版本；缺失时继续独立定位，不用 needs-info 阻断全部工作。
2. 默认 compact 控制台增加有界 task_event：题目出现/变更/结束；实际发出的 prompt、executeCmd、submitAnswer；新收到 llmResp、lastCmdResult、相关错误与动作回执；Agent generation/stage/stopReason/步骤计数变化。仅变化或实际发送时记录，不逐帧重复原文。
3. 每条带 run/team/round/event 关联和内容摘要、长度、哈希、明确截断标志。命令/回复先过滤凭据再截断；全文仍在现有本地 trace 的 request/response/decision。不得把猜测归属当作官方 request ID，间隔或缺失消息明确标注。任务结束仅表示观测或内部状态变化，没有真实判题/奖励不能打印成功。
4. 控制台不可依赖磁盘 trace 成功写入；日志失败不能改变官方响应。主 HTTP 回包后才处理诊断；状态、每字段字符量和流数量有界。跨阵营/进程/回合重置隔离；重复请求不刷屏，内容相同但新实际发送的命令仍保留。
5. 增加 `trace_tool.py tasks <日志目录> --output <文件>`，导出解题相关事件和出处、捕获缺口及包身份，去掉逐帧地图；原始日志不改。只读取日志，不执行模型/沙盒或策略，默认凭据过滤。即使没有任务也明确输出0和覆盖范围。
6. 验证手写请求序列的领取→题目→模型→命令→回执→答案→判题/结束、失败/长文/脱敏/重复回包/重置/红蓝隔离/磁盘失败；检查输出官方 JSON 完全不变。导出与实际 HTTP 路径测试，相关测试后完整回归及包验证再交付。

# 三类LLM任务 / P0b 共享调用与上下文底座 Spec v1

- 状态：下一阶段设计，尚未派单或实现；P0a审核后绑定新base SHA和manifest。
- 总约束：[LLM_TASKS_ROADMAP.md](LLM_TASKS_ROADMAP.md)。类别：官方接口实现修复/内部架构；R01、R02、R07，接口§1.1、§1.3.2、§1.7、§2.1。
- 本阶段目标：三类能力将来共用同一预算、在途请求和回执归属机制；不实现新的解题算法、新闻预测或宝藏推理。

## 1. 职责和接口

新增llm_router.py负责状态和调用选择；新增task_context.py负责构造有界、可序列化的输入上下文。planner.py持有它们的状态；brain.py在现有任务/角色策略后合并已批准的通道提案。sandbox.py仍承担官方返回值解析和基础额度记账，避免出现第二套独立日限计数。

建议内部接口（最终命名可调整，语义不得改变）：

- offer(owner, generation, source_digest, request)：提出请求，不消费额度、不改变官方响应。
- ingest(observation)：先处理公开任务有效性、跨日和上轮回执，再选择新请求。
- select(observation, confirmed_task)：最多选择一个新的认知通道操作，返回prompt或executeCmd的提案以及本地解释；普通角色动作仍独立生成。
- mark_emitted(proposal)：实际写入本轮响应时才记录尝试、在途请求与普通额度。发生网络写入不确定时保守预留，并记录不确定，不重复退款重发。
- dump/load/reset：状态跨模拟器JSON传输不丢失；未知schema拒绝相关上下文并降级为确定性策略，不能悄悄认为额度和历史为零。

新模块不得直接访问网络、调用外部模型SDK或运行子进程。平台通过prompt/executeCmd执行；本地适配器产生同形回执，读取结果必须走相同ingest路径。

## 2. 状态和关联

队伍级Agent共用本队已知事实；角色状态按role_id分别记录，但工人和开拓者不各自开一个LLM会话。自进化题按generation隔离，新闻和宝藏各自保留主题上下文；调用时组装当前工作所需字段。LLM普通额度在队伍层统一，不按角色倍增。另一阵营/对局的非公开状态、额度和在途请求不能混入。

每队维护：day_index、普通已用数/不确定预留数、active_generation、pending_llm、pending_command、候选请求队列、有限已处理回执索引。

每个待返回请求包含：内部request_id、owner（task/news/treasure）、generation、source_digest、sent_round、purpose、budget_class、expected_result_shape、最后处理状态。上下文包含题目原文及其哈希、答案格式约束、已观测事实、工具结果摘要及原始trace引用、失败记录、待确认问题。不收集或要求LLM隐藏推理链。

官方只给llmResp/lastCmdResult，没有承诺内部request_id回传。因此关联依赖本地单个在途请求和跨回合顺序；缺少可信归属时隔离结果，不猜配。允许在我们自己的模型JSON计划或命令输出中包含内部nonce以校验，但不能据此宣称平台支持request_id或绝不丢消息。

建议请求状态：queued → emitted → waiting → received / rejected / expired / obsolete。题目原文或接受周期变化形成新generation；相同题目文本再次领取也属于新一代。任务结束后不能将旧答案/命令输出提交给新题。

LLM响应不能只凭“非空且晚于sent_round”就自动认作当前新答案；覆盖重复旧结果、空结果、任务结束后到达、跨日到达和两侧交错观测的用例。同样文本可以是不同请求的有效结果，不能全局按回答文本去重。

## 3. 有效任务与额度

confirmed_task必须来自公开证据：phaseTask已有原文、活着的开拓者仍在该任务合法范围、已知任务未超时/结束，或一个有充分公开证据的恢复状态。isValid=false可能只是该点不可再次领取，不能据此独自结束已有任务。未知timeout不得当0直接到期，也不得假定永远有效。

未确认acceptTask期间，不因本地cycle对象存在就给新请求标记任务豁免。当前确认等待逻辑保留；没有确认或原文时不抢先调用模型求解不存在的题目。

普通额度为全队每天3次，按当前回合所属130轮游戏日结算；一个请求按发送日计数，结果第二天到达不再占次。已确认自进化任务内与该任务相关的调用不计普通额度。任务外请求不会因为另一条任务存在就伪装成任务请求。

普通额度用完仍可选择确定性游戏动作和合法任务；不能让整个角色控制器停摆。收到官方errorCode5时记录本地判断与平台拒绝不一致，在该日/该任务的后续请求上退避，不盲目重试；具体恢复条件需通过实际回执确认，先提供可配置的保守策略并标注非官方规则。

预览、offer和被更高优先级提案替换的请求不消耗额度。相同观测重复处理不得重复登记发送；HTTP重试下网络级exactly-once并非本地代码能保证，须明确保守策略及证据。

## 4. 失败和并发

- 每队最多一个LLM请求在途、一个命令在途；MVP串行发送依赖操作，不把多个prompt拼成不可关联的并行调用。
- 无回执采用有限等待和退避参数；这些是工程值，不冒充官方模型超时。超时请求进入expired，迟到回执进入隔离记录。
- 模型JSON解析失败、缺字段、截断、unsupported kind均不能生成新的游戏动作或Shell；最多有限次数请求修复，随后保留确定性策略/结束该求解尝试。
- 原文、工具输出、摘要长度与上下文总量均设软上限；裁剪保存原始trace引用和截断标志，不能删除未满足的关键约束后假装上下文完整。
- 上下文整理不允许在HTTP线程同步调用模型压缩。日志故障不能抛出到角色规划；请求本地计算应留足5秒回包裕量。
- pending状态与任务状态必须在每队范围内原子更新，单队重入不能覆盖；另一队不共享额度/回执。

## 5. 允许文件与验收

允许brain.py调度接缝、planner.py、sandbox.py、llm_router.py、task_context.py、对应测试，必要的telemetry允许字段及模拟器适配；不得改任务答案算法、数值、防御布局、官方原文、workflow脚本或包产物。

必须有不调用真实LLM的独立测试：

1. news与treasure共用3次普通额度；第4次不发；已确认task请求仍可用且普通余额不变。
2. acceptTask尚无原文时不获得豁免；死亡/离开/结束后恢复普通类别；有效任务的isValid=false不被误判为结束。
3. 第130轮发出、131轮回执：只计发送日一次；重复输入不重复消费；预览不产生pending。
4. 旧代际回复、同轮已有结果、空/重复结果不成为新题答案；两队轮流请求无串扰。
5. dump/load后保留原文、约束、在途归属和额度；旧/损坏状态显式降级，不伪造上下文恢复。
6. 模型/沙盒结果可确定性脚本注入；JSON计划中伪造工具或官方字段不被执行；任何失败仍返回合法roleCommandMap。
7. 新router关闭时现有默认策略与冻结公开观测响应相同；打开后仅改变批准的认知通道调度，角色互斥/预算仍通过审计。

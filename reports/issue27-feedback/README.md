来源：[新增实机片段](https://github.com/guihousun/Competition_HW/issues/27#issuecomment-5694722267)，运行版本8fa0625。修复包内源码：`1edb4979c206c0bf655e6bf07227fd653c8ed3e3`。
类别：策略/工程修复、日志工具；规则依据与验收见 [Spec](../../specs/ISSUE_27_FEEDBACK_LOOP.md)。不修改官方规则或示例原件。

## 修复及边界

1. 任务内记住已经明确判错的答案。只绑定已发提交与相邻轮errorCode 2；重排JSON键/空白无法绕过。新答案仍可提交，模型也可以继续读题、查询和校验。错误字段和值的摘要优先进入上下文，持久拒绝记录不依赖短期历史；跨任务清空。旧状态v2安全迁移到v3，不凭空恢复旧裁决。
2. 结构化HTTP回执增加当前页完整性诊断：10条/总12条、截断、业务错误、未知结构分别处理。401→400→200按最终200评估，不再把探测错误等同最终失败。它是补数提示，不是跨页集合证明，也不直接产出或验证答案。
3. 明确的复合命令末尾CRLF126，只有绝对cwd和受支持简单前缀时，自动提议兼容check。只重试check，不重做mkdir/写文件等前缀，不修改check原件；复杂命令交回模型处理。动作与工具次数限制保留。
4. 实包测试发现额外日志缺陷：HTTP先返回，后续线程可抢先更新TaskJournal，导致r2/r3被r4越过，任务check统计缺失。正式和本地HTTP入口改为写响应前预留日志顺序，写后交单一后台消费者汇总。日志输出不阻塞HTTP；有界队列满明确记丢弃；发送失败不记已发动作。

## 验证

最终检查清单、原始测试日志哈希和实际参赛包双阵营POST结果见同目录 `validation.json` 与附带日志/JSON。测试使用合成模型回复和独立fixture，不是模型正确率评估，也不是内网PASS。

保留失败证据：前一候选6de2010的Linux实际包check探针暴露了日志乱序，已定位并修复，不能用随后重跑通过掩盖；最终1edb497通过确定性并发测试及多次实际包探针。WSL的Bash对CRLF解释器缺失返回127，与用户平台126文字不同；回归用已记录平台126回执选择恢复，再在真实POSIX执行兼容check并检查文件及副作用不变，未声称覆盖所有127故障。

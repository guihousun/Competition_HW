## 第 1 步：能跑的空框架（HTTP 进出 + 空动作）

**目标** 把"平台 ↔ 我们"这条链路焊死：能收请求、能回合法响应，**不含任何策略**。
入口形态照抄 `example/CoreGeek/CoreGeek/`（**双层嵌套目录**）。

**产出** `main3.py`（读端口 → `chdir` → `src/` 进 `sys.path` → 起服务）/ `run.sh` /
`pyproject.toml`（`dependencies = []`）/ `web/server.py` / `app.py` / `game/planner.py`。
验证：`curl` 打样例 → 200 + 合法三字段、3ms（红线 5000ms）；
空 body / 坏 JSON / `GET /`（501，判题器只发 POST）/ 样例四种边界都不抛异常。
`run.sh` 加 `PYTHONUTF8=1` —— Windows 控制台默认 GBK，中文与 `→` 会乱码，
而日志是本地唯一的观测手段（判题机是 Linux，本就 UTF-8）。

## 第 2 步：看见局面，第一次发出真指令（解析 + 移动）

**目标** 把"解析 → 决策 → 编码 → 响应"整条管线跑通。行为刻意简单：**所有角色朝我方基地走一格**。

**产出** `protocol/model.py`（payload → `Turn`，**容错解析**：字段缺失/类型不对就丢掉那一条或退化，
绝不抛异常）+ `commands.py`（唯一知道线上指令形状的地方，第 3 步并进 `actions.py` 后删除）。
只解析这一步真会用到的字段；阻挡格 = 我方单位 + 敌方可见单位 + 中立元素 + 机器人，
外加**基地 2×2 的另外三格**（`pos` 是左上角）—— 只标一格会让角色**一头撞进基地里白扔一个回合**。

验证：三个角色各一条 `move`，**建筑没有出现在指令里**；7 条边界用例全过，
最值钱的两条是"贴着基地 ⇒ `{}`"与"两个工人相邻且目标同向 ⇒ 各自认领不同格"。
**踩到的坑**：`collections.abc.AbstractSet` **在 Python 3.13 已被移除** ⇒ `ImportError`，
进程直接起不来，而局部调用走不到那行 import ⇒ **只有起真服务才会暴露**
（这就是"每一步都必须真的把服务跑起来打一次"的来源）。

## 第 4 步：解析地图中立元素，工人走向石矿（跑通全流程）

**目标** 第 2 步发的指令**不读地图**，管线只通了一半。让工人奔一个真实存在于地图上的目标（石矿）。

**产出** `Turn.mines`（矿点 → 矿种；只有 `protocol/` 知道字段名）
+ `model._MINE_KINDS`/`_mines` + `planner` 改成"工人各自朝最近的石矿走一格"。
**走位与站位是同一件事**：矿格本身在 `blocked` 里，`step_toward` 走到**贴着矿的那一格**就自然返回
`None`，而那正好是 `collect` 的站位 ⇒ 不用写两段逻辑。`claimed` 防"两个人冲同一个空格"；
**不认领矿点**（两个工人挤同一座矿的不同邻格**都能采**）。
⚠️ 字段名是 **`neutralType`**，不是 `zoneType`；同一张表里的小贩/武器商店/任务点**不是矿但一样挡路**。

验证：单测 12 条。最值钱的是**收敛用例**（回合串起来跑 40 轮，最终 `dist == 1` 且此后不再产生动作）
—— **单帧"目标格算得对"证明不了走得过去、停得下来**，走歪、绕圈、贴住后抖动只有串起来跑才看得见。
起真服务 + 手工核对：`10010` **"什么都没做"正是正确行为**。

## 第 5 步：寻路换成 BFS 最短路

**目标** `step_toward` 从"贪心挪一格"换成 **BFS**：贪心只挑"确实更近"的格子，
遇凹形障碍会**停在原地不动**（不是走错，是**卡死**）。

**产出** 四条契约：**终点是"贴着 `goal` 的一格"而不是 `goal` 本身**（`goal` 通常挡路，
BFS 只在可通行格上展开 ⇒ 不需要特判）；**返回从起点迈出的第一步**；
`pos.dist(goal) <= 1` 提前返回 `None`（否则会被带到**另一个**贴着 `goal` 的格子白扔一条指令）；
`Turn.size` 缺失给 -1 ⇒ **单位不动，这是故意的**。

验证：单测 15 条，含"绕得过且**恰好 5 步**"（用步数钉最短）与"界外一步都不走"。
反向验证：把旧贪心抄回来 ⇒ 第二步就 `None`（卡死）；去掉边界检查 ⇒ 走出 `Pos(x=-1, y=4)`。

**仍生效的已知不确定性**
- **地图边界不在任务书 L85 的阻挡清单里**（那一列只有建筑/角色/机器人/中立单位/任务点/矿区）。
  贪心几乎撞不到，**BFS 会绕到图外去** ⇒ 取保守解：界外一律不走。
  越界算"指令非法"还是"执行失败"**文档没写 —— 不走一定安全**。
- **并列最短时取哪条取决于 `STEPS` 的探索顺序**：样例里 `(9,17)`/`(10,17)`/`(11,17)` 都是等长首步，
  测试钉的只是其中一条。**等长不影响正确性，只影响逐字节回归。**

## 第 6 步：把地图建成一个格子矩阵（`Turn.map`）

**目标** `Turn.blocked` 是扁平集合，看不出那一格是什么；且 `model.load` 对同一份 `mapInfo`
**解析了两遍**（两份真相迟早对不上，而症状是"以为能走、其实撞墙"）。改成每格只装一个**类别**。

**产出** `Map(size, entries)`：`.size` / `.cells`（`[y][x]`，**y 向上**）/ `.blocked` / `.stones` / `.render()`。
类别**原样取自 payload**，不查白名单 —— **未知类别照旧挡路**（判错方向只会多挡、不会放行）。
**不变量：非空即挡路**（任务书 L85）。构造收**稀疏** `entries`，稠密矩阵由 `Map` 自己铺。
`render()` 的字符表**是有损的**（机器人不分体型），`cells` 才是真相。
`Turn` 从 6 个字段瘦到 3 个（`station` 直接删，它只用来把基地展成 2×2）；
`model.py` 四趟分头扫 → **一趟铺 `entries`**（写入顺序即覆盖顺序：中立元素先写、单位后写）；
`grid.py` 一行未动。**顺带修掉一个真 bug**：基地 2×2 而 `pos` 只给左上角（接口文档明说"**双方**"），
旧实现只展开了我方基地 ⇒ 敌方基地只挡 1 格（`blocked` 32 → 35 格，方向是**多挡**）。

验证：单测 19 条。最关键的是 `test_blocking_is_exactly_non_empty`：**独立按任务书 L85 从 payload
重算一遍**阻挡集合（四路来源 + 基地 2×2），**完全不走 `Map` 的代码**，再与 `map.blocked` 比对 ——
它防的是"迁移中漏掉某一类挡路物"。**肉眼对一次图是唯一能发现 y 翻转的办法**
（图上一切"看着像张地图"，单测和实现可能一起错）。真服务响应与第 5 步逐字节一致。

## 第 7 步：工人建武器（`build` 落地，优先建在基地后方）

**目标** 第一条经济动作：**工人先建武器**，位置优先放在基地后方，让基地的 2×2 实体挡在武器与机器人之间。
顺序：加特林 → 电磁狙击炮 → 火箭发射台；上限取"武器数 < 总角色数"。
**顺带把第 3 步欠的账还上**：`build` 是**闸门第一次真的挡住东西**。

**产出** `Build`（`roles = WORKER`）；`grid.weapon_cells(base)` / `back_weapon_cells(base, width)`；
基地 2×2 的展开从 `model` 搬进 `Map.__init__`；`Turn.gold` + `is_day`
（`round_no` 缺失给 -1 ⇒ 判成夜里 ⇒ 不建造）。
`planner` 每回合按优先级择一：① 建武器（已在邻格就发 `build`，否则走一格 —— **复用 `step_toward`，
天然停在邻格**，即"站位即建造位"）；② 否则朝最近石矿走一格。
**金币按递减预算扣**，不写成 `gold >= 25 * 待建数`（那样金币只剩 25 时会一座都不建）。
`sites`（已认领建造格）与 `claimed`（本回合落脚格）**分成两个集合**。新增 `_emit` 统一收口越权。

验证：单测 31 条。合成白天开局串着打 ⇒ **恰好 3 座**、顺序 `gatling/railgun/rocket`、
**全部在 `x=9`**、75 金归零。**踩到的坑**：合成局面上 `build` 一条没发 —— 实际是端口上挂着
一个上一轮遗留的服务进程（Windows 允许 `SO_REUSEADDR` 并存），请求打到了**旧代码**上
⇒ **起服务前先确认端口上只有一个监听者**。

**仍生效的已知不确定性**
1. **可建造区公式来自图片**（`docs/pic/build_map.png`），任务书正文没有。算错 ⇒ 建造失败；
   失败大概率算"执行失败"不计异常，但**未确认**。
2. **武器 `name` 的取值只对 `wall` 有实证**，武器名是从 `roleType` 表推的。
3. **机器人刷新方向只来自示意图**，正文未写。判据封装在 `_front_back` 一处，首场后按实测翻转。
4. **武器上限口径原文冲突**（表格"每种 ≤3"合计 9 座 vs 补充说明"全局最多 3 座"）。取保守的全局 ≤3。

## 第 8 步：工人采石、砌围墙（`collect` 落地 + 回合预算）

**目标** 补完策略指导第一天主线的后半句（最近的石矿、必须在晚上前把墙砌好、墙面向机器人进攻的方向）。
用户定的三条：**攒多少石头不写死**（每回合实时算，留 5 回合容错）；
**背离机器人那一侧的中间留缺口**；**夜里回基地走到武器旁边待命**。

**产出** `grid.wall_cells(base, width)`（**16 格，按建造优先级排**：正面列 → 顶行 → 底行 → 背面两角）；
`Collect`（`roles = WORKER`，`targetPos` 是**矿石的坐标**而不是站位）；
`BaseRole` 收窄成带 `stone`（`backpack` 是物品名数组、重复即计数，**不读 `backPackCapability`**）；
`within = (roundNo-1) % 130 + 1` + `day_rounds_left`（**含本回合**）；
`planner._stones_to_mine`（`d_mine + d_wall + 2s − 1 + 3k ≤ 白天还剩的回合 − TIME_MARGIN(5)`，
每多采一块**净**花 3 回合，再与"还差几格墙"取小。距离用**切比雪夫**）；
`_to_weapon`（夜里按距离取最近的一座**没被本回合别人认领**的武器，贴着就停）。

验证：单测 45 条（含**开拓者构造 `Collect` 抛 `PermissionError`**）。合成白天端到端：
回合 4/6/7 三座武器 → 采石 30 次 → 16 格墙 → 回合 66 空指令（环满了，手里还剩 3 块留给第二天）。

**踩到的坑（这一步最值钱的一条）：两个工人 26 回合来回踱步，一格墙都没砌**
根因是一行过滤：`_ring` 把"工人脚下那一格"也当挡路的格划掉了。`model._entries` 会把
`teamOur.roles` **写进网格**，所以"谁站在哪"也进 `blocked`；工人恰好站在一个**还没砌的墙格**上时，
那一格就从候选表里消失 ⇒ 另一个工人的 `free[0]` 整体后移、掉头去砌更靠后的墙；
等前一个工人一挪窝目标又变回来 —— **两人对着改目标，永远在原地互指**。
修法：**自己人站的那一格不算挡路**（只是路过，下一回合就走）；已砌的墙/中立元素/机器人照旧排除。
教训两条：① **手搓 `Map` 的合成局面里角色不在 `blocked`**，只有 `model._entries` 会把他们写进网格
—— 新用例第一版就是这么写的，于是它**连旧代码都放过去了**；
② 这类"多人互指"的死循环单帧断言看不见，得把回合串起来跑，**并且反向验证一次**。

**仍生效的已知不确定性**
1. **`collect` 没有实证报文**（`docs/response.txt` 里没有），形状是从接口文档推的。
   **它是不是真的没有昼夜限制，也没实测过。**
2. **回合预算里的距离是切比雪夫**，绕障时低估 —— 靠 5 回合余量吸收，**未实测**。
3. **夜里机器人打不打野外的工人** —— 决定缺口会不会变成"机器人进环"。留缺口是用户既定的取舍：
   正面完整、背面开口，而武器列（`x=9`）与基地紧贴缺口内侧。（第 17 步把缺口从 4 格改成整列 6 格。）

## 第 9 步：每回合复盘日志（先地图、后动作）

**目标** 判题器是黑盒、**不给任何别的视角**：出了事故手边只有一条 `move`，看不出当时场上是什么局面。

**产出** `app._log(turn, cmds)`（放"红线所在"的文件，日志的开关与降级必须和报文格式同一处管）
+ `protocol/actions.describe(cmds)`（字段名只有 `protocol` 知道，与 `to_wire` 一写一读）
+ 一条 `assertLogs` 用例钉住**顺序与内容**。
**关键设计**：`_log` 写在 **`try` 里面** —— 日志代码再不起眼也是代码，逃出去的话
`web/server.py` 的 `do_POST` **不接异常** ⇒ 连接直接断掉 = 判题器那边"响应超时"（红线第一条）。
**退化成空指令只是丢一个回合，断连接是整个资格。**

验证：单测 46 条；新用例按**逐字**断言抬头、行数、动作串，钉住"先地图后动作"的顺序。
起真服务顺手对图：`w`/`#`/`p` 的位置与 `docs/request.txt` 一致 ⇒ **行序没翻反**。

**仍生效的已知不确定性**
- **stdout 会不会把管道写满** —— Windows 管道缓冲 64KB，判题器若**不读**子进程 stdout
  就会阻塞在 write 上 ⇒ 响应超时 ⇒ 直通红线。**本地判题环境没跑过，这是唯一没被实测过的实质风险**
  （历次字节数变化见 `CLAUDE.md` 硬约束 5 与文末总表）。

## 第 10 步：夜里操炮防守（`attack` 落地，三个角色各认领一座武器）

**目标** 第 8 步把工人夜里"走到武器旁边待命"做完了，但**待命本身不产生任何效果**。
用户要求"**所有角色**（上限三个）回来操作武器"。两条策略：**开火优先级 = 射程内血最少的机器人**
（并列时打近的）；**机器人还没走进射程时站在炮位待命**（不发指令，空指令合法）。

**产出** `world.py` 新增 `Weapon` / `Robot` 两个 `NamedTuple`，`Turn` 多两栏（**带默认值 `()`**）；
`map.py` 删掉 `Map.weapons` 与 `WEAPON_KINDS`（它没有 id/射程/冷却，留着就是两份真相）；
`model._weapons` / `_robots` / `_destroyed`（**没有 `teamOur.weapons` 这个 key**，
武器和角色混在同一张表里靠 `roleType` 分流）；`Attack`（`roles = ALL`），`describe` 补 `controllerId`；
`planner`：昼夜分岔、`_to_weapon` 改名 `_defend`、新增 `_fire`、`_emit` 开 keyword-only 的 `key`。
`tests` 46 → 66 条，新增 `_records` / `_terrain` 两个夹具（**记录是唯一真相，地形由它推**）。

**四个坑（都是"发得出、判题器说不"那种）**：① **`attack` 的 key 是武器 id**，操控角色在
`controllerId` 里 —— 与其它动作**反着来**；② **`round_no` 缺失时一条都不发**（`is_day` 把缺失的
回合号判成夜里，那个降级方向对"白天不许建造"安全，对 `attack` 就反了）；
③ **先按射程过滤、再取血最少的**（顺序写反就成了"拿全场最弱但打不着的那个当目标"）；
④ **已毁的炮 / 阵亡的角色不发指令**（`health == 0` ⇒ 丢；用 `== 0` 而不是 `<= 0`，
因为字段缺失是 -1）。`attackRange` / `cooldown` 的缺省值方向**故意相反**：
射程 -1 ⇒ 够不着 ⇒ 不开火；冷却 -1 ⇒ 照打。

验证：单测 66 条。**反向验证 4 条**（优先级换序 / 射程 `<=` 改 `<` / 删掉冷却判断 / `_emit` 的 key
换回角色 id）。**逐字节回归：样例这一次必须变（变了才是对的）** —— 开拓者现在也发指令，2 条变 3 条。
**合成夜战端到端**：三件事一次看全 —— **key 是武器 id**（`20000`/`20001`/`20002`）、
`controllerId` 是角色 id、三座炮**集火打同一只**。

**仍生效的已知不确定性**
1. **`cooldown` 字段样例里没有**（三座炮都缺）。真机 payload 若也没有，"冷却期不开火"永远不生效。
   接口文档与官方 demo 两处独立确认了这个字段，只能按"该有"来写。
2. **`attackRange` 是 3/6/10 还是样例的 4/7/INT_MAX** —— 以 payload 为准。
3. **L1 加特林/火箭只传 1 个目标是否合法** —— 文档写"数量与等级数相同"，自洽；
   "少传算不算非法"没写。
4. **白天发 `attack` 到底算不算异常** —— 文档只说"非法/不可用"，没列进 §8 的异常清单。我们按"算"来防。
5. **已知代价**：**角色数 < 武器数时火力打折**（开拓者被任务钉住 ⇒ 夜里三座炮只有两人操，
   打折 1/3）。由任务积分覆盖，首场赛后调。

## 第 11 步：开拓者做任务（`acceptTask` → 问判题器 LLM → `submitAnswer`）

**目标** 第 1~10 步白天只有工人在动。任务书 §5.3：开拓者到**己方任务点**周围一格内 `acceptTask`，
任务原文出现在下一回合 payload 顶层的 `phaseTask`，答案通过 `submitAnswer` 交回。
收益量级完全不同：任务是 `积分奖励 + 5 × 标准回合数 / (实际完成回合 − 接取回合)`
（**越快交完奖励越高**，以乘法计；样例两个点各 50 分 + 30 金），而杀一台机器人只有 1~10 分。
唯一确定存在的智能通道就是响应里那个至今恒为空串的 `prompt` 字段 —— 发给判题器的 LLM，
下一回合在 `llmResp` 里回来。

用户定的四条：范围 = 接任务 + LLM 求解闭环（**不做沙盒**）；**不发 `executeCmd`**；
**无状态**；提示词 = 让题目自己说话。

**产出** `Turn` 加三栏，全带默认值（既有 66 条用例零改动）：`task_points`（本回合**可接取**的己方任务点）
/ `phase_task`（任务**原文**，**非空 = 手上有任务**，这是"任务进行中"的唯一判据）/ `llm_resp`（**要提交的答案原文**）。
`model._tasks` / `_text`，`_pos` 加 `key` 参数（任务点是**唯一**叫 `taskPosition` 的）。
**`playerTasks` 是任务点的权威来源**（只含我方 2 个点、只认**锚点格**就够 ⇒ 不必去 `zones` 里认
`challengerTaskPoint*`、也不必读 `teamOur.type`）。
字段缺失的降级方向**故意不是"少做"**（与 `_gold`/`_size`/`_stone` 相反）：误接一个冷却中的点只是
**指令执行失败**（不计异常），而误判成"永远接不了"会让整条任务线**静默作废** ⇒ `isValid` **明确为 `False`**
才排除，`coldDownRounds` 缺失给 -1、按 `<= 0` 也算就绪。
`AcceptTask` / `SubmitAnswer`（**都仅开拓者**，**报文里都没有 `targetPos`**，领哪个点由**站位**决定）。
`planner.plan()` 的循环分四支，**"钉死"那一支放在最前面**（全局最早的判据，与昼夜无关；判据用
**载荷事实** `phase_task` 而不是自己记的"谁领了任务"）；新增 `_take_task` / `_answer_task` / `prompt_for` + `TASK_PROMPT`。
`app.py`：`prompt_for(turn)` 接进响应顶层，`_log` 在任务存续期间多打一行。

验证：单测 94 条，**反向验证 7 条**，最值钱的两条：把"钉死"挪到夜间分支**之后** ⇒ 开拓者真的被拉去
开炮、**任务当场作废**；`describe` 改回硬读 `cmd["targetPos"][0]` ⇒ **两条用例一起炸**（含端到端那条）。
**合成端到端 6 个局面**（真 HTTP）：接任务时报文**没有 `targetPos`**；`phaseTask` 非空时开拓者
一条指令都没有且 `prompt` = 模板 + 任务原文；有 `llmResp` 时发 `submitAnswer`；
同一份"有 `llmResp`"的 payload 连打三次都是 `submitAnswer` —— **无状态设计的预期行为，不是 bug**。

**仍生效的已知不确定性**
1. **答案格式完全未知** —— 本步最大的单点风险。通过率按"字段个数"算 ⇒ 是多字段结构化答案，
   但字段名、分隔符、是否要 JSON，文档一个字都没有。`PROMPT` 的措辞是**唯一的杠杆**。
2. **`llmResp` 的生命周期未知**（"没发 prompt 时是空串"还是"保留上一次"）。设计对两种都成立，但没实证。
3. **跨任务时会多交一次上一个任务的答案**（`llmResp` 若仍是旧的），一回合后自愈。
   代价一个回合 + 一次 errorCode 2。
4. **`timeoutRounds` 样例里没有** ⇒ 不做任何"值不值得接"的时间预算。
5. **白天发 `acceptTask` 是否合法**（§4.4 那格没写昼夜限制）。我们只白天接；
   若实测证明夜里也能接，是另一条策略（早接早完成，速度奖励是**乘法**的）。
6. **"周围一格"是否含对角**没写。按切比雪夫（含对角）—— 与全局的距离度量一致。

## 第 14 步：把判题器的回执记进日志（`errors` / `lastRoundRoleActionResults`）

**目标** 用户要求"把任务信息打印出来，看看是什么情况"。查下来发现两处：任务那一行是 `phase_task[:120]`
的**静默**截断（看不出后面还有没有内容）；**判题器对任务的判决从来没被读进 `Turn`、更没进过日志**
—— 日志里只有"我们发了什么"，没有"判题器认不认"。所以这一步不是"多打点字"，
是补上整条诊断链最关键的一环。

**产出** `game/world.py`：`Error` NamedTuple（`__str__` = `f"{code}：{description}"`）
+ `Turn.errors` / `Turn.action_results`。**`errorCode` 不翻译成文字**（那 5 个码是**协议知识**，
写进代码就是一份会跟接口文档漂移的第二真相；码表只活在 `CLAUDE.md` 的领域事实里给人读日志用）。
**`action_results` 原样保留、不剪枝**（含我们不操控的基地格）。
`protocol/model.py`：`_errors` / `_action_results`，两条解析各有一处**故意的严格** ——
`errorCode` 解析不出来 ⇒ **整条丢掉**（`-1：xxx` 会被读日志的人当成"未知错误 0"去查一个不存在的问题）；
`value` **只认真正的 JSON 布尔**（JSON 里的 `"false"` 是**非空字符串**，`bool("false") == True`）；
key 转不成 `int` 的丢掉。
`app.py`：`_log` 加三块（判题器报错 / 上回合未通过 / 任务行），`_clip` 替掉静默截断
（超长打 `…（共 N 字）`，**上限单位是字不是字节**）。

验证：单测 113 条，**反向验证 5 条**全中。真服务端到端：样例响应逐字节不变；
合成的"任务在身 + 判题器报错"回合里**截断标记与真实字数对上了**（1066 = 66 + 200×5）——
这正是"静默截断"修好的证据。

**仍生效的已知不确定性**
1. **`errors` 是"本轮"的**（接口文档 §1.7 原文）：它报的其实是**上一回合**那条指令的结果。
   这一点文档没有直说（"本轮产生的错误信息数组"里的"本轮"指哪一回合），
   实测时要用"我们发了什么 / 它报了什么"对齐一次才能确定。
2. **任务原文会有多长完全不知道**。`LOG_TEXT_MAX = 400` 是个**估的**数。真跑起来若发现任务普遍超过
   400 字，截断标记会直接告诉我们"共 N 字"，照那个数调这一个常量 —— 这就是把截断**说在脸上**的用处。
3. **"任务期间每回合打同一段任务原文"是这一步最大的字节浪费**（占任务期间日志的一半以上）。
   一个不改策略、不加状态的省法是把 `LOG_TEXT_MAX` 调小；要既省又不截断就得给 `app` 加跨回合状态，
   **代价是日志不再自明**。现在的取舍是**日志优先**：诊断工具的可预测性比几个字节重要。

## 第 15 步：采矿落实（"保持够砌墙的石头量，然后选价格最高的矿"）

**目标** 兑现 `docs/策略指导.md`（用户手改）里的第二条。
**"然后"是顺序，不是并列** —— 墙只吃石头，若一上来就挑最贵的铜，围墙永远砌不成。
所以：**墙上还缺石头** ⇒ 只认石矿、取最近的；**墙砌完了** ⇒ 才按**收购价**挑最值钱的矿。
"保持够砌墙的量"那一半本来就有（`_stones_to_mine` 拿"还差几格墙"当上限），
本步的新行为只有后半句：**砌完之后工人原本原地闲置，现在转去采矿**。

**产出** `Map.stones: frozenset[Pos]` → **`Map.ores: Mapping[Pos, str]`**（矿点 → 矿种，
新增 `ORE_KINDS` 与 `STONE`；**小贩/武器商店/任务点照旧只进 `blocked`**）；
`Turn.vendor_prices`（`vendorShopList` → 矿种→收购价，只收 `price >= 0`）；
`_nearest_stone` → **`_pick_ore(pos, ores, prices, *, want_stone)`** + 新增 **`_mine_spare_ore()`**；
`tests` 113 → 119 条。
**`ores` 带矿种、价格从载荷读** —— 同一条理由（"铜 > 铁 > 石"**不是常量**，写死的排序在事件期间
恰好是错的），见 `CLAUDE.md`；价目缺失/矿种不在表里 ⇒ 按 0 算 ⇒ **不为它多走一步**。
`_mine_spare_ore` 的往返预算参照点换成**基地**（不是工地）—— 墙砌完后没有工地可回了，而夜里的炮位就在基地四周。

验证：单测 119 条。**反向验证 5 条全中**。
⚠️ **`test_the_ring_decides_whether_price_gets_a_vote` 的第一版是假通过的**：它原本让工人"朝矿走一格"，
而 BFS 的第一格常常**同时靠近两座矿** ⇒ 改坏 `want_stone` 也照样过。改成"两座矿各贴在工人一边、
断言 `collect` 瞄的是哪一座"之后才真的挂了那一次。**"走一格"这种断言测不出方向，只有坐标级别的答案测得出。**
**合成端到端**：样例价目（石 1 / 铁 3 / **铜 5**）⇒ 两人都朝**铜矿**；**只把价目翻成 铁 9 / 铜 5**，
同一份局面重发 ⇒ 两人双双掉头朝**铁矿**。**这才是"价格来自载荷"的端到端证据。**

**仍生效的已知不确定性**
1. **"墙砌完了"是常态还是例外完全不知道。** 若 16 格一般在第 40 回合就砌完，那每天能多出 30 个回合的
   劳作；若拖到第 68 回合才砌完，它基本不会触发（往返预算会把远矿全否掉）。
2. **`vendorShopList` 是"收购价"这件事是**推断**（接口文档 §1.1 只给了元素形状 `{name, price}`）。
   若它其实是**售价**，那"按价排序选矿"仍然成立，但"价 0 的矿不去采"这条会误伤。
   **下一场实测时对一下金币数。**
3. **挖矿点的"采满 10 次就消失"没有计数**（payload 没有剩余次数字段）。真跑起来若发现工人对着空矿位
   一直 `collect`，症状是 `action_results` 里翻 `false` —— 那时再想跨回合计数的办法，现在加就是预先抽象。
4. **同价矿的取舍只按坐标排**：两个工人可能挑中同一座矿的相邻格，这是允许的（矿不认领），
   但会让两个人整天黏在一起 —— 若实测发现"两个工人总是同进同出"，再考虑按工人 id 错开。

## 第 16 步：给任务线接上沙盒（`executeCmd` + `lastCmdResult`）

**目标** **用户从日志里找到了任务一直失败的真因**：响应里那个 `executeCmd` 是"让判题器执行的 shell 命令，
由 LLM 回复生成"，所以拿到任务后要和 LLM 交互、给它一个 `executeCmd` 工具、把生成的命令放进响应顶层，
**拿到执行结果之后才知道任务要什么**。核对文档判断完全正确，而这是一条**从来没有接过的通道**：
`src/` 里 `lastCmdResult` **零出现**、`executeCmd` 恒为 `""` ⇒ 答案只能靠 LLM 硬猜
⇒ 判题器只能报 `errorCode 2`。**这就是任务线 0 分的根因。**

**产出** `Turn.cmd_result: str = ""`；`model.load()` 接上 `lastCmdResult`；
**本步主体在 `planner`**：`prompt_for` 删除 → **`task_channel(turn) -> (prompt, executeCmd)`**
+ `_asked` / `_is_tool_reply` / `_tool_command` / `_retry_note`；`TASK_PROMPT` 重写成三段式；
`app.handle` 改成写响应顶层的 `executeCmd`，`_log` 新增**沙盒行**；`tests` 119 → 135 条。

**六条判据的状态机**（从上往下先命中先返回）：① 没任务或名册里没有开拓者 ⇒ 两个都不发；
② `cmd_result` 非空 ⇒ 回灌结果、**这轮绝不发命令**；③ 工具给了命令 ⇒ 发命令、不提问；
④ 判题器报 `code 2` ⇒ 带"上次答错了"重问；⑤ 是答案 ⇒ 都不发；⑥ 否则只把题目问出去。
核心不变量 = **两条通道互斥**（同一轮既提问又发命令 ⇒ LLM 拿着过期结果作答 ⇒ 活锁），
这也是把它合成一个函数而不是 `prompt_for` + `execute_for` 的全部理由。
② 必须压在 ③ 前面、纠错做成修饰符而非分支、`executeCmd` 的闸门要显式补 —— **三条理由都在 `CLAUDE.md`**。

验证：单测 135 条，**反向验证 8 条全中、无假绿**。
⚠️ 这一轮**反向验证抓出了一处真冗余**：`_retry_note` 里原本写的是
`return reply if reply and not _is_tool_reply(reply) else ""`，但去掉 `reply and` 行为**完全相同**
⇒ 按"禁止冗余设计"删掉了那个 `and`。
⚠️ **还原只用备份文件，绝不用 `git checkout`** —— 那会退到 HEAD、把本步所有未提交的改动一起抹掉。
**合成一整条任务链路**（逐回合只改 `phaseTask` / `llmResp` / `lastCmdResult`）：
提问 → `executeCmd == 'python -c "print(1+1)"'` → prompt 含 `[exitCode:0]\n2` → `submitAnswer: 晴 26 度`。

**仍生效的已知不确定性**
1. **`<tool>…</tool>` 是我们自己定的协议，判题器认不认完全不知道**（任务书只写了沙盒"能跑基础的
   shell 与 python 指令"，**没规定 LLM 该用什么形状要命令**）—— 这是**最大的单点风险**。
   若不认，症状是 `executeCmd` 一直发出去、`lastCmdResult` 一直是空 ⇒ 退化成第 15 步的状态。
2. **`llmResp` 粘不粘，文档一个字没写**。自检判据：日志里"沙盒：回「…」"连续两回合出现同一条
   ⇒ 要么粘住了，要么判题器真的重复执行 —— 两种都说明这条链要重新想。
3. **`lastCmdResult` 会不会粘住**同样没实测过。它若也粘，判据 ② 会**每回合都命中** ⇒ 任务线永远停在
   "回灌结果"、再也不发新命令 —— 症状同样在日志上。
4. **沙盒执行若延迟超过一回合，判据 ② / ③ 的互斥就失准**：`cmd_result` 与 `llmResp` 会错开一回合到达，
   我们会在等结果的回合里把那条命令**再发一遍**。判据 ② 只挡住了"同回合"。
5. **任务切换那一回合，`cmd_result` 里装的是旧任务的输出**（判据 ② 只认"非空"）。**已知、暂不修**
   —— 要修就得引入跨回合状态。
6. **回灌全文可能撑爆判题器 LLM 的 prompt**（沙盒输出上限 64KB，全文回灌等于把 64KB 塞进下一轮）。
   用户拍板"全文回灌"，若实测发现 LLM 因此答不出来，这里的取舍要重新谈 —— **`_clip` 早就在手边**。
7. **判题器执行 `executeCmd` 的 15 秒限时与"不计异常"这两条没实测过**（L210 是文档承诺）。
   若实际会计异常，那这条通道的每一次使用都在赌红线的 5 次 —— 那是**必须立刻回退**的事。

## 第 17 步：围墙只砌三面（背面整列留成"门"）+ "不能把工人关起来"的闸门

**目标** 用户原话："墙只建立前面的，最后一排都不建立，建墙有一个原则，**不能把工人关起来**，
如果可能出现，需要工人先走出来"。两条拍板：围墙范围 = **14 格**（正面列 6 + 顶行 4 + 底行 4，
**背面整列 6 格含上下两角，一格都不砌**）；"不能把工人关起来"做成**运行时的闸门**，不靠几何自动保证。
⚠️ **门那 6 格里没有任何建筑**（后列炮位在**武器环**的后列，不在围墙环的背面列）⇒ 能堵门的只有**单位**。

**产出** `grid.py`：`wall_cells` **16 → 14 格**（顺序逐格不变）+ 新增 **`box_cells(base)`**（36 格）
与 **`step_outside(pos, box, blocked, size)`**（BFS 与 `step_toward` 同构，只把终止条件从"贴着 goal"
换成 **`nxt not in box`**）。`tests` 135 → 151 条。

**闸门两半**（都在 `planner.plan` 的一次调用里）：**(1) 会关人就一格都不砌** —— `_trapped` 逐角色问
"**假设墙砌满**（`_walled`）之后还出不出去"，返回要救的 id 集合 `leaving`，`gated` 传进 `_build_walls`；
⚠️ 那一处 `if gated: return` 的位置在 `if not free:` **之后** —— "环上无可砌（⇒ 去采最值的矿）"与
"闸门挡住了"都会让 `free` 空掉，含义却相反（前者是**砌完了**，后者是**还没砌完、这一回合不许砌**）。
**(2) 要被关住的人先走出来**（`plan` 的角色循环里，任务钉死那一支之后）：
⚠️ **两半用的是两套障碍**（`leaving` 按"假设砌满"判、迈出去那一步按"**现在**"判，
两套之差恰好是那 14 格里还没砌的部分）；⚠️ **`turn.is_day` 不能省**（夜里那一支只会把人从炮位上拉走）；
⚠️ **`| claimed` 不能省**（两个要走出来的人会被指到同一格 ⇒ §4.5.4 目标争夺 ⇒ 两人都不动）；
⚠️ **`_walled` 把自己人算成障碍，`_ring` 把自己人算路过 —— 这两处故意相反**。

**`_step_aside`（"站在目标格上先挪开"）是 e2e 才揪出来的**：`model._entries` 把单位铺在**最后**，
于是人站在墙上时网格里只剩 `worker`、**墙被盖掉了**；而 `_ring` 的"自己人算路过"又把它复活成候选
⇒ `free[0]` 永远是脚下这一格 ⇒ **每回合对同一格 `build`，永远轮不到下一格、石头白花，`free` 也永不为空**
（连"砌完了去采最值钱的矿"那一支都进不去）。修法：`role.pos == target` ⇒ 这一回合只 `move`、
**下一回合再砌**；两个方向都收敛。
**`_dead_ends` 实现过又删掉**：穷举 69,132 个局面，**用与不用的踪迹完全相同**，而它还会把"现在走得通"
的格当障碍、拉长或否决合法路径 ⇒ 按规则 1 删除。

验证：单测 151 条。**反向验证 11 条改坏全部被抓住**。
⚠️ **还原只用备份，且每次改完代码要重新 `cp` 一份**（旧备份会把新改动一起抹掉）。
**60 回合驱动**：14 格全部砌上、与 `wall_cells` 顺序一致、正面列最先；第 37 回合有 `movePos`
（站在刚砌好的格上 ⇒ 先挪开），第 38 回合从邻格砌上。
⚠️ **驱动脚本第一版是错的，差点得出错误结论**：它只跟踪了 1 号工人，另外两个角色的指令被丢掉，
于是"只砌了 13 格、工人掉头去采铜"看起来像策略 bug —— 实际是**另一个工人已经认领了最后一格**。
教训：**模拟判题器必须跟踪全部角色**，且 `acceptTask` / `submitAnswer` **没有 `targetPos`**。

**仍生效的已知不确定性**
1. **闸门 (1)/(2) 在今天这条几何下几乎打不着**（要门那 6 格**同时**被单位堵满，而我方至多 3 个角色）。
   它的价值是兜底。**下次复盘若发现日志里从没触发过，这是设计如此，不是坏了。**
2. **闸门 (2) 有时会被 `_mine_spare_ore` 抢功**：盒外有矿、且该工人这回合本来就要去采，
   那条路径也会把人带出盒子。(2) 是**保证**而不是常见路径。**未实测。**
3. **闸门 (1) 是"全有或全无"**：门被堵时哪怕只剩最后一格墙也**整回合不砌**。副作用是墙可能停在 13/14 格。
4. **"假设墙砌满"把我们的角色也算成障碍格**：光靠自己人仍关不住人，但**叠加机器人**时会提前触发
   （少砌一回合墙）。**未实测**，症状是"墙莫名停在 13 格"。
5. **门开在背面，机器人从正面进来后仍可从门绕出去**。本步把缺口从 4 格放宽到 6 格且**挪到了整列**，
   等于把"绕出去"的通道挪离了正面火力线。**影响未实测**，首场若发现机器人绕圈不挨打，第一嫌疑是它。
6. **"站在目标格上先挪开"白花 1 回合**。比它更省的做法是"把脚下那一格从自己的候选里剔掉"，
   但那会漏掉"脚下正好是**最后一格**没砌的墙" ⇒ 工人站在上面干等、墙永远停在 13/14（静默停摆）。

## 第 18 步：Agent 系统（`agent/` + `tools/`）+ 任务线切到新工具协议

**目标** 用户原话（要点）：独立 `agent/` 文件夹 + 其中的 `tools/`；提供 `executeCmd(cmd)` 工具；
提供 `SOP2Prompt(SOP)` 让 PromptSOP 自进化；接到任务时触发 Agent 的 `chat` 组装上下文；
解析 `llmResp` 里的 `<tool><tool_name>…</tool_name><tool_param>…</tool_param></tool>`；
提供顶层的 `tool_call(tool_name, tool_param)`；无需工具时用 `<answer>…</answer>` 包裹答案；
Prompt 模板 = `# Agent定位 / # 可使用的工具 {{tool_desc}} / # 输出格式 / # 沉淀的 SOP {{SOP}}`。
第 16 步的 `<tool>…</tool>` 形状是**我们自己定的**，且当时只有"一条裸命令"、没有"工具"这个概念 ——
这一步把工具**注册化**。四条拍板：位置 = `src/coregeek/agent/`；SOP = 跨回合状态（全项目**唯一**一处）；
**同一步把任务线切过去**（新形状**取代**旧形状，不建"暂时没人调用"的子系统）；
**全覆盖兼容**（旧形状照旧当 `executeCmd`；没有 `<answer>` 就**原文当答案交** —— 这是新协议不被认账时唯一的退路）。

**产出** `agent/__init__.py`（新建，0 字节）/ `agent/chat.py`（`PROMPT` 四段模板 + `chat()` +
三个谓词 `tool_of` / `looks_like_tool` / `answer_of` + 共用的 `_block`）/
`agent/tools/__init__.py`（`TOOLS` 注册表 + `tool_call` + `tool_desc`）/
`agent/tools/cmd.py`（`executeCmd(cmd)` —— **原样返回**，一个赋值都不做）/
`agent/tools/sop.py`（`SOP2Prompt` / `current` / `reset` / `SOP_MAX=1000` + 内容变化时一行日志）；
`planner.task_channel` 换料（判据链顺序不变）；`tests` 151 → 187 条。
依赖方向新增 **`game/planner.py → agent`**，机械保证是 **`chat(request: str, …)` 收字符串、不收 `Turn`**。

**三个谓词的分工**（宽严两端，细节见 `CLAUDE.md`）：`tool_of` **严格**（名字与参数**成对**才给
`(名, 参数)`；**两个都没有 ⇒ 整块正文当一条 `executeCmd` 命令** = 旧形状兼容层）；`looks_like_tool`
**宽**（`"<tool" in reply`）；`answer_of` **三级兜底**（有标记只认块内容 / 像工具回复给空 / 否则原文即答案）。
⚠️ **`answer_of` 是「该提交什么」与「该骂什么」的同一个谓词**（提交 / 纠错内容 / 判"已有答案"三处共用）
—— 一旦分家，纠错段会把**带标签的原文**喂回去，LLM 看到自己上次的标记被原文骂回来，行为未定义。
**铁律：`tool_call` 的返回值就是那条要进 `executeCmd` 的命令**（`""` = 不产出命令 / 调用不成立，**下游不需要区分**）；
它是**副作用唯一发生点**，写在判据链之前 ⇒ 走"回灌结果"那一轮 SOP 照样生效。**`executeCmd` 不执行任何东西**
（执行者是**判题器的沙盒**）。**`SOP2Prompt` 是整段替换不是追加**（追加没有遗忘机制）；内容没变就不吭声。

验证：单测 187 条。**反向验证 21 处改坏，21/21 全中**。
⚠️ **第 12 条一开始是假绿**：改坏把描述写死成一个**仍然包含两个工具名**的字面量 ⇒ 行为等价；
修的是**用例**，不是改坏脚本。
**字节预算**：最坏局面实测 **44 行 / 6180 字节**（任务在身 + 沙盒结果顶格 + SOP 刚更新），上限钉在 6900。
**真服务九轮 e2e**（每一条都验了）：② `SOP2Prompt` 不发命令**且存下的 SOP 立刻出现在同一轮的 prompt 里**；
⑤ **交上去的是块内容 `晴 26 度`，不是 `<answer>` 原文**；⑥ 纠错段含 `晴 26 度` 且**不含**标签；
⑨ 畸形回复**不发命令、不提交、prompt 非空**（两条通道都不哑火）。
**全局断言**：任何一回合都没有同时出现非空 `prompt` 与非空 `executeCmd`。
⚠️ **这份 e2e 里的"LLM"是我们自己写的** ⇒ 它只证明"我们的解析与编排自洽"，**不证明判题器认这个形状**。

**仍生效的已知不确定性**
1. **最大单点风险：判题器的 LLM 认不认这个形状。** 兼容层把"不认账"的后果压到"退化回第 16 步"，
   但"LLM 用第三种形状"仍是敞口。**首场自检判据**：任务行"提交："里若**不是** `<tool_name>` 形状
   ⇒ 形状没被采纳 ⇒ 回退只需改 `tool_of` 一处。
2. **SOP 一旦存错就是整场的事**（没有重置机制、没有遗忘）。最坏 = LLM 往 SOP 里灌了一段有害的"套路"，
   此后每回合 prompt 都带着它。后果是**答得差，不是异常**。**未实测**。
3. **SOP 不按任务分区**：任务 A 沉淀的 SOP 会灌进任务 B 的 prompt。用户拍板的取舍，记录、不修。
4. **`SOP2Prompt` 那一轮走判据 ⑥ 重问**：LLM 若反复调它（`llm_resp` 粘住），会退化成"每回合重问、
   永不提交"。**升级触发条件**：首场日志若出现「同一任务连续 ≥3 回合 `llm_resp` 都是 `SOP2Prompt` 调用、
   且始终没有 `submitAnswer`」⇒ 升级成"显式 ack"编排。**未实测。**
5. **`<answer>` 被解包后提交，等于改了交上去的字节**（第 16 步是原文进原文出）。**未实测**。
   裸文本兜底保证"没有 `<answer>` 时行为与第 16 步一致"。
6. **畸形 `<answer>`（空块 / 半截）改成了"不提交 + 重问"**：代价是那一回合没有提交
   （判题器取"通过率最高"的那份，所以不提交不扣分）。**未实测。**
7. **`planner → agent` 是新的依赖边**：若将来 `agent` 需要 `Turn`/`Pos`，这条边会变成双向 ——
   那时应该把"什么时候说话"也搬进 agent，而不是让 agent 认识 `game`。
8. **`SOP_MAX = 1000` 是拍的**，没有实盘依据。首场看 `SOP 更新：存 N 字` 那一行的 N 分布。

## 第 25 步：任务内全量会话上下文（`Context`）

**目标** 用户拍板：agent 太薄弱，要做上下文管理 —— **同一个 task 同一个上下文**，新建 `Context`
类放独立文件，管理 system prompt / user / assistant 等完整会话信息，**先不压缩、全量**，
注入 Agent。设计先行呈报（两条决策点均按推荐落定：无新内容重问轮追加「请继续。」；
消息标题 `【题目】`/`【你的回复】`）。

**产出** 新叶子 `agent/context.py`（`Context`：`task` 身份 + 消息表 + `feed`/`nudge`/`hear`/`render`，
零包内 import）。`Agent.chat` 变**编排**：题目变了 ⇒ 新会话（构造即问：首条 user = `【题目】`）；
回灌轮 `feed`（两个标题逐字沿用旧模板）；无新内容的重问轮 `nudge`（`Context.NUDGE` =
「请继续。」—— 判题器 LLM 是黑盒，会话停在它自己的输出上是个含糊指令）；system（四段模板）
**每轮现刷**（SOP 是活的，③′ 的回执不能冻在构造时）。新增 `Agent.hear`：`task_channel`
每回合把 `llm_resp` 记进会话 —— **发命令（③）/交答案（⑤）那轮没有 prompt 也得记**，否则回灌那轮
LLM 的命令凭空消失；**粘住去重**（与最后一条 assistant 相同 ⇒ 跳过，`llmResp` 按粘住设计的再利用）。
`chat.py` 的自由函数 `chat()` 删除（无第二调用方），`PROMPT` 只剩四段 header，尾巴由
`Context.render` 接 `# 对话记录`；三个谓词一字未动。**判据链 ①–⑥ 与三个 `AGENT.chat` 调用点
一字未动**（planner 侧只多了 `AGENT.hear(reply)` 一行）。`reset` 清两处状态（SOP + 会话）。
渲染是**拼接不走 `str.format`** ⇒ 消息正文里的 `{}` 永远安全（原 `chat()` 的同一条铁律平移）。

**会话记原文、纠错块记解包件**：prompt 里从此有两份"它说过的话" —— `【你的回复】` 收整段原文

验证（TDD：先挂后写，两轮 RED）：第一轮 6 个行为用例对着旧代码挂（4 个 `hear` 缺失的
AttributeError + e2e/`task_channel` 的会话断言）；第二轮 `ModuleNotFoundError`（模块缺失）。
GREEN 后 **227 条全绿**（新增 `ContextTest` 7 条 + `ChatPromptTest` 5 条 + `task_channel` 1 条；
`chat()` 直调的 3 处改写到新 API；删 1 条对象消失的用例 `test_the_assembly_needs_sop_and_tool_desc`）。
**字节预算重测**（同一脚本在 HEAD worktree 的旧版上能量出第 23 步记的 6170/8861 ⇒ 量法可信）：
带提问的回合 +2~3 行（`# 对话记录` 标题占的物理行），最坏 **75 行 / 8944 字节**（上限 9300、
余量 356；字节反而略降）。`app._log` docstring / `CLAUDE.md` 硬约束 5 / 预算用例三处已同步。
真服务一局（`run.sh 18085` + 样例 payload 四连发）：① 首问 = 四段 header + `# 对话记录` +
`【题目】`；② 命令进 `executeCmd`、无 prompt；③ 回灌轮的 prompt 里**有它自己的工具调用**

1. **prompt 无上界增长（用户拍板"先不压缩"）**：极端 = 多轮 64KB 沙盒回执全量进 prompt ⇒
   响应体巨大、判题器侧 LLM 推理变慢 ⇒ **响应超时是红线第一条**；判题器对 `prompt` 字段的

2. **「请继续。」与「# 对话记录」的措辞都没实测过**：判题器 LLM 对"会话停在它自己的输出上

3. **同文任务续会话**：冷却后同一道题再现 ⇒ 续上旧会话（设计如此：它记得试过什么）。

4. **`llmResp` 粘住只是推断**：去重靠"与最后一条 assistant 相同"。若判题器其实**每回合清空**
   `llmResp`（不粘），去重只是白设一道（无害）；若它粘住的时点与推断不同，极端情况下
   会漏记一条真回复（同文、且恰在粘住窗口内）。

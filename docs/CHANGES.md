## 第 20 轮（2026-09-12）

### C20-1　任务刷新改为"按任务点"（官方实现修复，R07）

- **规则依据**：任务书 §五——"每个任务点的任务总数有上限，在任务执行结束后，再次接取任务
  需等待 30 个回合刷新时间"。刷新属于**任务点**，不属于队伍。
- **改前行为**：`_maybe_accept` 有一道全队冷却闸门（`cooldown_until`），任一任务结束后
  30 回合内拒绝**所有**接取，包括另一个完好可用的任务点。且该闸门只存在于保留记忆的路径上，
  无状态的判题请求反而更接近规则。
- **改后行为**：只看判据本身——按点的 `isValid` 与 `coldDownRounds`；全局冷却不再阻止接取。
- **行为例子**：种子 3 第 16 回合在点 A 完成任务；第 17 回合点 A 变为 `isValid=false,
  coldDownRounds=30`，点 B 仍 `isValid=true`。改前开拓者空等到第 47 回合；改后第 18 回合
  即前往点 B 接取。
- **验证方式**：`tests/test_tasks.py::PipelineFrameTests::test_refresh_delay_is_per_point_not_global`
  （冷却中的点不可接取；记忆里的全局冷却不阻止另一个可接取的点）；
  五个种子双方压力 1 基准：任务结算 108 → 129，总分 2588 → 2637，10 个配置
  `audit_errors` 全空。
- **已知代价**：开拓者在任务循环里停留更久，宝藏在部分种子（如种子 1，窗口 184–224）
  会错过时间窗。已在 `docs/VIEWER.md` 与 VALIDATION.md 记录。

### C20-2　宝物行程的窄条件优先（策略优化，R07）

- **规则依据**：任务书 §5.2——"一张地图宝藏只有一个，成功开启后，后续继续开启则不会获得
  宝藏奖励"。宝物是一次性的，任务点在刷新后还会回来。
- **改后行为**：仅当"已买得起献祭物品"或"窗口已开且来得及赶到"时，宝物行程才占用开拓者；
  否则让位给任务循环。
- **验证方式**：`tests/test_treasure.py::PursuitTests`（传闻必须出现在请求里；种子 19 走完
  购买→前往→召唤）；曾实测无条件优先会低 150–260 分，因此刻意收窄。
- **诚实标注**：种子 1 不再断言开启——那取决于调度而非机制。

### C20-3　三条运行路径的一致性验证（验证工具，非规则变更）

- **背景**：第 19 轮发现调试页因 planner 无法跨 JSON 往返而**每回合重建**，等于在跑失忆策略。
  本轮的对比脚本证实修好之后：判题 POST / 调试页（带 planner 往返）/ 直接驱动
  在相同记忆下逐回合完全一致（状态指纹与事件都相同）。
- **新增测试**：`test_viewer_transport_matches_a_direct_run`（把调试页自己携带的记忆喂给
  直接驱动，任何差异都是真实缺陷）、`test_state_less_requests_still_run_the_task_loop`
  （无状态请求也必须能领取/提交/得分）。
- **自我纠正**：这两条测试我先后写错过两次——先给判题路径塞了失忆 planner，又要求两条路径
  逐步同事件（保留记忆会合法压制重复的 `acceptTask`）。最终断言的是真正成立的性质。

## 第 19 轮（2026-09-12）

### C19-1　planner 记忆可经 JSON 往返（官方实现修复 / 本地工具，R01）

- **问题**：`_viewer_state` 把存活的 planner 换成摘要，`_json_safe` 又把它变成类型名占位符；
  浏览器把状态发回来时无法重建，于是**网页每回合新建一个空 planner**。任务周期、30 回合冷却、
  LLM 额度因此只在判题路径上保留——网页跑的其实是另一套策略。
- **改后**：`PlannerState.dump()/load()`（JSON 安全、容忍残缺输入）；`_json_safe` 对带
  `dump()` 的对象取真实数据；`step()` 用 `PlannerState.load` 重建；`_viewer_state` 回传完整记忆。
- **验证方式**：`test_tasks.py::PlannerPersistenceTests`（往返、JSON 可序列化、残缺输入容错）、
  `DebugTransportTests`（调试传输必须保留任务冷却/周期）；浏览器端种子 19 在第 92 回合开启宝藏，
  与判题路径一致（`reports/screenshots/13-treasure-opened.png`）。

### C19-2　`_treasureRound` 是回合内标记，不得回传（官方实现修复，R01）

- **问题**：该标记写在调试响应里，浏览器原样送回，此后每回合都以为宝物仍占用开拓者，
  任务行走被全程压制。
- **改后**：从 `_viewer_state` 与 `step_payload` 两侧剥掉，并登记在 `HW.viewModel.roundScopedKeys`。
- **验证方式**：`test_viewer.py::round-scoped signals never reach the browser state`；
  浏览器端确认不再泄漏。

### C19-3　事件与文案的真实性（UI工具）

- **问题**：`acceptTask`/`submitAnswer`/`summonTreasure` 在事件流里完全没有描述（新机制对用户不可见）；
  开火文案仍写着"本地简化命中，未计算弹道遮挡"，而弹道早已实现——这是**不实陈述**。
- **改后**：三种动作都有可读描述并新增"任务"过滤类；开火文案按真实来源说明（直线弹道/导弹不被阻挡）。
- **验证方式**：`test_viewer.py`（动作有分类与可读描述、旧文案不得回归）。

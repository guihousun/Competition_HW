# Issue 29 两种宝藏时间表的验收参考

来源：[用户补充评论5757771651](https://github.com/guihousun/Competition_HW/issues/29#issuecomment-5757771651)。变更类别：测试与资料补充，涉及R06/R07；不修改运行策略、官方原文或模拟器规则。

| 地图标识 | 四条线索出现日 | 开放起点 | 用户给出的地点 | 需要物品 |
|---|---|---|---|---|
| `attack_map_update_long_context_mission` | 第1、2、3、4天 | 第5天白昼开始，即r521 | (3,3) | 古符石板、烈焰之息、星辰之沙各1 |
| `attack_map` | 第1、3、5、7天 | 第8天白昼开始，即r911 | (3,3) | 同上，各1 |

两例未明确关闭时刻。“第5/8天白昼开始开放”不能自动解释成当夜关闭或永久开放。当前结构要求完整起止窗口才能执行召唤；关闭时间未确认时保留 `window` 未知及原始开放线索，不伪造 `closesAt`。这也意味着只有这些补充资料，尚不能证明现有程序能自行领取这两例宝藏。

现有模型提示包含任务书§4.6.3的商品名称和外观参考，以及本轮商店观测。古符石板的协议枚举保持官方拼写 `AcientTablet`，不纠正成 `AncientTablet`；烈焰之息为 `FlameBreath`，星辰之沙为 `StarSand`。这些对应关系用于理解商品，不把本例三材料组合设成所有地图固定配方。

新增 `tests/test_issue29_updated_timelines.py`：

- 将用户解释作为明确标注的验收摘述，分别按两种发布时间表逐日输入；每次模型上下文只能包含已经出现的线索。它不是平台完整新闻的逐字副本。
- 有界脚本模型回执在缺截止时返回未知窗口，验证开放当天及入夜后均不会凭空召唤。
- 独立的**合成执行对照**额外提供“当夜关闭”这一假设，仅用于测试完整计划从第5天或第8天触发，避免把r521写死为所有地图答案。该关闭时间不是Issue资料，不进入默认运行源码。
- 用两个独立对局状态回放两图，拒绝第二图引用第一图独有的开放线索；不把上一局答案或未出现的未来传闻塞进当前观测。

这些测试验证上下文、引用校验和动作调度。脚本回执预先给出结构化解释，**不是实LLM自主解谜成功或官方实测领取成功**。后续仍应读取当局新闻、实际商店列表及召唤反馈；若官方允许未知截止下尝试，需要独立确认规则与风险策略，再讨论实现。
